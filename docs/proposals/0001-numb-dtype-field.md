# 提案 0001：`.numb` 头部的 dtype 字段宽度与码值

- 状态：**已定案（方案 A）**，2026-11-25 落地；结论已回写 `docs/DATA-FORMAT.md` §3.2
- 影响面：`docs/DATA-FORMAT.md` §3.2、后续 `.numb` 读写实现（Go / C++ / Rust）、fixture 落盘
- 归属：D1 定稿后的**破坏性变更**，须走 §9.2

## 1. 背景

`docs/DATA-FORMAT.md` §3.2 的头部表写「偏移 6，长度 **1** 字节，dtype 码」，
而同一节的 dtype 码表给出的码值是 `b` / `i1` / `i2` / `i4` / `i8` / `f4` / `f8` / `u1` / `u2` / `u4` / `u8`。
除 `b` 以外都是**两个 ASCII 字符**，塞不进 1 字节。规范自相矛盾，实现无法开工：
按 1 字节读会把 `f4` 读成 `f` 加后续字节错位；按 2 字节读又与头部表冲突。

目前仓库里**没有任何 `.numb` 实现**（`grep NUMB` 只命中文档），因此现在改的代价最低。

## 2. 候选方案

### 方案 A：dtype 码固定 2 字节 ASCII（推荐）

- 头部：`magic(4) | version(2) | dtype(2) | ndim(1) | shape(8×ndim) | data`
- 码值保持表里的写法，`b` 补成 `b1`（1 字节布尔），其余 `i1/i2/i4/i8/f4/f8/u1/u2/u4/u8` 不变
- 读侧按 2 字节精确匹配，未知码报错（符合 §4「旧读取器遇未知码必须报错」）

**优点**：码值与现有文档基本一致（只把 `b` 改成 `b1`），十六进制 dump 里可读；实现只需一次比较 2 字节。
**缺点**：头部从 8 字节变 9 字节（`8 + 8×ndim` 变 `9 + 8×ndim`），文件长度公式要改；`b` 改名是破坏性改动。

### 方案 B：dtype 码固定 1 字节单字符枚举

- 码值改为单字符：`b`(bool) / `c`(int8) / `h`(int16) / `i`(int32) / `q`(int64) / `f`(float32) / `d`(float64) / `B`(uint8) / `H`(uint16) / `I`(uint32) / `Q`(uint64)
- 头部保持 8 字节

**优点**：与头部表「长度 1」自洽，头部长度不变；单字符映射是 C 语言整型后缀的惯例。
**缺点**：`f` / `d` 之类看不出位宽，需要查表；文档里现有的 `f4` / `i8` 写法全部要改。

### 方案 C：1 字节「类型 + 宽度」位域

- 例如高 4 位类型（0=b、1=i、2=u、3=f）、低 4 位宽度（1/2/4/8）
- **缺点**：自定义编码，dump 不可读，排错成本高；不推荐。

## 3. 推荐与影响

推荐 **方案 A**：改动集中在「`b` → `b1`」和「头部 8 → 9 字节」两处，码值本身保持可读；
由于没有任何实现，迁移成本为零。

定案后需要同步：

1. `docs/DATA-FORMAT.md` §3.2 的头部表、码表、文件长度公式；
2. `tests/contract/NAME-MAP.tsv` 若登记了 `.numb` 相关语义（当前没有）则补行；
3. 新增实现：Go `io/numb.go`、C++ `numb.h`、Rust `src/numb.rs`，各自带往返用例；
4. fixture 是否改用 `.numb` 属于后续独立提案（当前 npz 已够用）。

## 4. 待裁决问题

1. 采用 A 还是 B？（C 不建议）
2. 若选 A，布尔码用 `b1` 还是保留 `b` 并定义为「2 字节 `b` + 0x00」？（后者更丑，不建议）
3. 是否顺带把 `version` 提为 2（因为头部长度变了）？
